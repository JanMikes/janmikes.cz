The simplest GitLab CI pipeline ever

Continuous integration sounds like a project of its own. In GitLab it starts with one file and three lines of YAML. The goal of this talk was simple: share my CI experience and show how little you need to begin.

A quick show of hands

I started with some quick research in the room. Who knows GitLab exists? Who uses GitLab? Who automates anything with CI?

Three lines

Here is the simplest GitLab CI pipeline ever:

greeting:
  script:
    - echo "Hello PHPPrague 2018!"

Commit this as .gitlab-ci.yml in the root of a GitLab repository and you have CI. greeting is the name of a job, script is the list of shell commands it runs. That’s it.

The result: one job from master, finished in 49 seconds, queued for one second. The pipeline shows a single green greeting job in the default Test stage. The job log (slightly shortened) tells the whole story:

I didn’t pick a Docker image, so the shared runner on GitLab.com used its default one, ruby:2.5. I didn’t install or configure a runner either. Wasn’t that simple?

How does it work?

The .gitlab-ci.yml file is all you need. GitLab sees it on every push, creates a pipeline, and hands its jobs to runners. Every job goes through the same lifecycle:

  1. choose a Docker image,
  2. git clone the repository,
  3. pass in artifacts from earlier jobs,
  4. run the script,
  5. upload its own artifacts.

Artifacts are files a job keeps after it finishes, for example an installed vendor/ directory, so later jobs don’t have to build it again. Each job starts in a fresh container, so artifacts are how jobs share work.

A multi-stage pipeline

Real projects need more than one job, and some jobs have to wait for others. That’s what stages are for: jobs in the same stage run in parallel, and the next stage starts only when the previous one succeeds. A typical PHP setup:

stages:
  - build
  - test

composer:
  stage: build
  image: composer:1.3.2
  script:
    - composer install
  artifacts:
    paths:
      - vendor/
    expire_in: 24h

phpstan:
  stage: test
  image: php:7.1
  script:
    - composer phpstan

The composer job installs dependencies in the official Composer image and saves vendor/ as an artifact for 24 hours. The phpstan job runs in a plain PHP image, gets vendor/ passed in, and runs static analysis. Each job picks the image that fits it.

Where it can go

The same file scales up to this: 12 jobs in five stages, with code quality, dependency and security scanning, a staging deploy, and a production rollout to 10%, 25%, 50% and then 100% of traffic.

GitLab is much more than Git

Git hosting is only the start. GitLab covers the whole cycle: plan, create, verify, package, release, configure and monitor. CI is the “verify” part.

And the timing was right. A few weeks before the talk, imports of GitHub projects into GitLab jumped from hundreds a day to 46,900 on 4 June, 98,300 on 5 June and 113,900 on 6 June. That was the week Microsoft announced it was buying GitHub.
