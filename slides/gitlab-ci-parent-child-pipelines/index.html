CI in a monorepo with GitLab parent-child pipelines

CI v monorepu pomocí Gitlab parent-child pipelines. One .gitlab-ci.yml for a whole monorepo grows until nobody wants to touch it. GitLab lets one pipeline start other pipelines in the same project, and even generate them on the fly.

We used this setup in production at Carvago and Sharry, so this isn’t a toy. The talk had four parts: what a parent-child pipeline is, what a dynamic child pipeline is, the use case (a monorepo), and a live demo. A shorter, demo-focused version of the same topic was also at WarpCamp 2021.

What is a parent-child pipeline?

GitLab already had multi-project pipelines, where a job in one project triggers a pipeline in another project. Parent-child pipelines, introduced in GitLab 12.7, do the same within one project. In the words of the GitLab docs: a pipeline can trigger a set of concurrently running child pipelines, but within the same project.

A child pipeline is just a job with the trigger keyword. The simplest version points at another YAML file in the repository:

microservice_a:
  trigger:
    include: path/to/microservice_a.yml

The include can be a list, and it can mix local files with GitLab’s built-in templates:

microservice_a:
  trigger:
    include:
      - local: path/to/microservice_a.yml
      - template: Security/SAST.gitlab-ci.yml

Or it can take the child configuration from a different project, for example a shared pipeline library:

microservice_a:
  trigger:
    include:
      - project: 'my-group/my-pipeline-library'
        file: 'path/to/ci-config.yml'

Why bother?

These are the problems that show up as a single pipeline grows, and the ones parent-child pipelines solve:

  • Too big .gitlab-ci.yml. The one global configuration becomes very long and hard to manage.
  • Inefficient blocking stages. With classic stages, every job in a stage must finish before the next stage starts. A slow test for one part of the repo holds up the deploy of a completely unrelated part. Each child pipeline still runs its own stages in order, but it doesn’t wait for unrelated jobs in the parent.
  • Imports complexity and collisions. Splitting the file with include helps with length, but all included files share one namespace, so job names can collide and jobs can get duplicated by accident.
  • Pipeline UX. One pipeline with dozens of jobs and stages is hard to read in the UI. Child pipelines group related jobs together.

Dynamic child pipelines

The second half of the idea: instead of running a child pipeline from a static YAML file, you write a job that runs your own script to generate the YAML, save it as an artifact, and trigger a child pipeline from that artifact.

generate-config:
  stage: build
  script: generate-ci-config > generated-config.yml
  artifacts:
    paths:
      - generated-config.yml

child-pipeline:
  stage: test
  trigger:
    include:
      - artifact: generated-config.yml
        job: generate-config

The generator can be anything: a shell script, a PHP script, whatever you like. It can look at the repository, decide what needs to run, and write only those jobs. That’s the real power. The pipeline is no longer a fixed list of jobs, it’s the output of a program.

The use case: a monorepo

A monorepo keeps many packages or services in one repository. That’s exactly where one big pipeline hurts the most: every package adds its own test and deploy jobs, the file keeps growing, and stages block each other across packages that have nothing in common.

With parent-child pipelines, each package gets its own child pipeline. With a dynamic child pipeline, a script can produce the configuration for all the packages, so adding a new package doesn’t mean copy-pasting another block of YAML.

Live demo

The rest of the talk was a live demo (“what could go wrong”). It starts from a small PHP monorepo with packages A, B and C and a single flat pipeline with build, test and deploy jobs for each package, and turns it into parent-child pipelines.
